# StayEd — Session Summary (2026-08-23)

Summary of everything changed in this working session, grouped by feature. File paths are
relative to the repo root. None of this is committed to git yet.

## 1. Learner Profile — Modality display + change history

Learner Profile now shows "Modality: X (Since [date])" instead of just a static label. The Edit
Learner modal has a real Modality dropdown; changing it prompts for an optional reason and logs
the change. Every change shows up as a "Modality Changed" entry in the Monitoring History
timeline (e.g. "Face-to-Face → Modular — Reason: Schedule constraints").

**New DB migration:** `StayEd_Backend/sql/13_modality_change_log.sql` — new `modality_change_log`
table (enrollment_id, old/new modality, reason, changed_by_teacher_id, change_date).

**Backend:** `app/routes/learner_routes.py` (`update_learner` logs changes; `learner_profile`
computes "since" date and merges changes into the timeline).

**Frontend:** `pages/teacher/learner-profile.html`, `assets/js/teacher/learner-profile.js`,
`assets/css/pages/teacher/learner-profile.css`.

## 2. Email format validation

Registration, Forgot Password, and the profile email field all now reject malformed emails
(client-side and server-side) instead of silently accepting anything.

**Backend:** `app/helpers.py` (new `EMAIL_RE`), `app/routes/auth_routes.py`,
`app/routes/user_routes.py`.

**Frontend:** `assets/js/auth/forgot-password.js`, `assets/js/teacher/profile-settings.js`.

## 3. Real email sending (Gmail SMTP)

Built a real mailer using Gmail SMTP. Two things now actually send an email instead of doing
nothing:
- Approving a pending teacher registration → "Your StayEd account has been approved"
- Rejecting a pending teacher registration → "Your StayEd registration was not approved"

Both fail silently (logged, not shown to the admin) if SMTP isn't configured, so approving/
rejecting always still works even with no email set up.

**New file:** `StayEd_Backend/app/services/mailer.py`.

**Backend:** `app/config.py` (SMTP_* settings), `app/routes/admin_routes.py` (`approve_user`,
`reject_user`), `.env` / `.env.example` (SMTP_HOST/PORT/USERNAME/PASSWORD/FROM_EMAIL/FROM_NAME).

**Setup needed:** a Gmail address + an "App Password" (myaccount.google.com/apppasswords, needs
2-Step Verification on) in `StayEd_Backend/.env`. Already configured and tested working this
session.

## 4. Ticket 3 — Face-to-Face Attendance Checklist

New feature: teachers can schedule meet-up dates for a class and record attendance as a simple
checklist (check present learners, one Save for the whole class). Only shows for classes that
actually have Face-to-Face/Blended learners. Reopening a saved date lets you correct it without
creating duplicate records.

**New DB migration:** `StayEd_Backend/sql/14_session_attendance_audit.sql` — adds
`recorded_by_teacher_id` and `updated_at` to the existing (previously unused) `session_attendance`
table.

**Backend:** `app/routes/class_routes.py` — new endpoints: `GET/POST /classes/<id>/sessions`,
`GET/POST /classes/<id>/sessions/<id>/attendance`. Also fixed `teacher_class_cards()`'s modality
detection, which was using a crude MAX() guess that could hide the attendance button on classes
that do have F2F learners.

**New file:** `StayEd_Frontend/assets/js/teacher/class-attendance-modal.js`.

**Frontend:** `assets/js/teacher/class-management.js` (new "Take Attendance" button on class
cards), `pages/teacher/class-management.html`, `assets/js/core/api.js`.

## 5. Ticket 4 — Planned Module Return Date + Overdue Tracking

Modules now get a "Planned Return Date" at release time (auto-suggested from a configurable
default duration, editable), and show a red "Overdue by N days" flag once that date passes with
no return recorded. Does **not** touch the Random Forest model — purely a UI/monitoring signal,
per the ticket's explicit instruction.

**New DB migration:** `StayEd_Backend/sql/15_module_planned_return.sql` — adds
`planned_return_date` to `module_record`, plus a new `default_module_duration_days` system
setting (starts at 21 days).

**Backend:** `app/routes/learner_routes.py` (`release_module_batch` auto-calculates the planned
date; new `PATCH /learners/<id>/module-batches/<id>/modules/<id>` to edit it after the fact;
`_logbook`/`learner_profile` compute overdue status + an "Overdue Modules" count),
`app/services/settings_service.py` (get/set default duration), `app/routes/admin_routes.py`
(`GET /settings/module-duration`, `PUT /admin/settings/module-duration`).

**Frontend:** `assets/js/teacher/module-management-modal.js` (planned-return field on release,
inline edit-in-place on each module, Overdue badge), `pages/teacher/learner-profile.html` +
`assets/js/teacher/learner-profile.js` (new "Overdue Modules" stat), `pages/admin/settings.html` +
`assets/js/admin/settings.js` (new "Module Return Default" control under the Academic Year tab).

## What needs to be set up again

### Database
Nothing manual — `db_bootstrap.py` auto-applies migrations 13, 14, and 15 on next backend start.

### Backend config
SMTP is already configured in this machine's `.env` and tested working. On a different machine,
`SMTP_USERNAME`/`SMTP_PASSWORD` need to be filled in again (see `.env.example` for the format) or
approval/rejection emails will just silently skip sending.

### Not yet built (deliberately out of scope this session)
- No system-wide MM/DD/YYYY date format sweep — only the new fields added this session use it.
- No separate "Module Definition" catalog table — planned return dates live on the existing
  per-release module record.
- No class-wide "N learners have overdue modules" dashboard widget.
- No full per-learner attendance history timeline (the existing aggregate attendance-rate stat
  will now populate with real data instead of always showing 0%, since nothing wrote to
  `session_attendance` before this session).
